I Built the Website. But I Forgot One Important Thing.

By Sakshi Madgundi · 2026

I used to think that the hardest part of creating a website was getting everything to work.

The design has to look right. The buttons have to work. The pages have to be responsive. The functionality has to connect properly.

And yes, all of that matters.

But my first client project taught me something that I didn't think about enough in the beginning:

A website doesn't stop being a product just because the developer has finished building it.

The project I was trying to solve

For my first client project, there was already an application with its own design and user experience.

My task was to bring that existing experience into WordPress and make the website work with the same visual direction.

So my focus was very clear:

  • Match the existing design
  • Recreate the required pages
  • Make the interactions work
  • Make the WooCommerce functionality live
  • Keep the website visually close to the original application

And I did what I set out to do.

The website worked. The pages looked right. The custom UI was there. The functionality was connected.

But there was one question I didn't ask early enough.

What happens when the client wants to change something after I am finished?

I focused too much on making it work

Because I wanted precise control over the design, I ended up hard-coding many parts of the website.

At the time, this made sense to me.

If I controlled the HTML, CSS, JavaScript and page structure directly, I could reproduce the design exactly the way I wanted.

And technically, that approach worked.

The problem wasn't simply that I used custom code.

The problem was that I didn't think enough about who would need to edit that content later.

THE WEBSITE LIFECYCLE
BUILD → LAUNCH → MAINTAIN → IMPROVE

Hard-coded doesn't automatically mean maintainable

There is nothing inherently wrong with custom coding.

Custom development is often exactly what a project needs.

The important question is:

Which parts should be controlled by the developer, and which parts should be controlled by the client?

For example, a custom layout or complex interaction may need developer-controlled code.

But a product name, product image, price or description is something a business owner may need to change regularly.

Then comes the uncomfortable part

Imagine the client wants to change the price of a product.

Or replace its image.

Or update the description.

Or change a promotional message.

If all of that information lives directly inside custom code, the client may have to come back to the developer for every small update.

And that's where I realized something important:

The website may be working perfectly for the developer, while still being inconvenient for the person who owns it.
A SMALL CHANGE SHOULD STAY SMALL
CHANGE PRICE → EDITOR → SAVE

The website should belong to the client

This is probably the biggest thing I would approach differently now.

When a developer creates a website for a business, they're not just delivering a collection of pages.

They're delivering something that the business will continue using after the project is handed over.

Businesses change.

Products change.

Prices change.

Images change.

Promotions change.

New content gets added.

Old content needs to be removed.

So the website needs to be prepared for that reality.

Custom design and editable content are not opposites

This is another distinction I understand much better now.

A website can have a completely custom design while still giving the client control over the content that they actually need to manage.

Developer-controlled

  • Page structure
  • UI / UX
  • Responsive layout
  • Complex interactions
  • Custom functionality
  • Technical integrations

Client-editable

  • Product names
  • Prices
  • Product images
  • Descriptions
  • Promotional content
  • Business information

The goal isn't to make every single thing editable.

The goal is to make the right things editable.

Maintenance is much bigger than fixing broken pages

Before this project, I thought about maintenance mostly as something you deal with when something breaks.

But maintenance can mean much more than that.

Content maintenance

Products, prices, images, descriptions, banners, contact details and other business information can change over time.

Technical maintenance

WordPress, themes, plugins, WooCommerce, PHP, JavaScript and third-party integrations all need attention as a website continues to evolve.

User-experience maintenance

A button that worked months ago might become broken. A mobile layout might need adjustment. A page might become outdated.

Security and reliability

Updates, backups, permissions and the overall health of the website also become part of keeping a site running properly.

MAINTENANCE IS PART OF THE PRODUCT
CONTENT Update
TECHNICAL Maintain
UX Improve
SECURITY Protect

A website is not a poster

A poster can be designed, printed and finished.

A website is different.

It lives.

It changes with the business.

That's why I now think about a website more like a living product than a finished file.

Launch day is not the end of a website's life. It's the beginning of its maintenance cycle.

What I would do differently today

If I were rebuilding that project today, I wouldn't start by asking:

"How can I hard-code this page?"

I'd start with:

"Which parts of this page should the client be able to control?"

Then I would design the implementation around that answer.

The visual experience can still be custom. The UI can still match the original application. The interactions can still be custom-built.

But the content that changes regularly should have a sensible editing system behind it.

The question I should have asked first

BEFORE BUILDING Who will need to change this later?

That one question can change the entire way a website is planned.

Because you're no longer thinking only about how to make the website work today.

You're thinking about how someone else will use it tomorrow.

From website developer to website partner

This project changed how I look at web development.

The job isn't simply:

DESIGN → CODE → DEPLOY

It's closer to:

UNDERSTAND → BUILD → TEST → LAUNCH → MAINTAIN

And maintenance isn't just another service you can mention after the website is complete.

It should be considered while the website is being built.

The lesson I took from one project

I don't look back at the hard-coded parts of that project and think the entire approach was useless.

It taught me something that I probably wouldn't have understood as clearly from a tutorial.

A developer doesn't only build for today's requirements. They build for the person who has to use the system tomorrow.

And tomorrow, the client might want to change something.

That's when maintainability stops being just a technical detail and becomes part of the product itself.

THE TAKEAWAY Build it well.
Make the right things editable.
Maintain it after launch.

Because a website isn't really finished when you publish it.

It's finished when it's built to live.
